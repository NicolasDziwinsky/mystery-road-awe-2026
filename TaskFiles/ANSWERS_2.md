Demo 2

A plain static file server simply serves files such as HTML, CSS, JavaScript, and images to the browser. It does not process or transform the application's source code.
Vite's dev server does more. It serves ES modules and transforms the code on demand, and it also provides features such as Hot Module Replacement (HMR). For example, when a source file is changed, Vite can update only the affected module instead of requiring the whole page to be reloaded.

Hot Module Replacement allows Vite to update a module in the browser while the application is running, without doing a full page reload.
When I changed the source code, the affected part of the application was updated immediately in the browser. The page itself did not perform a full reload, so the existing application state was preserved. For example, if a counter had already been incremented, its value remained instead of being reset as it would be after a normal page reload.

An application already split into ES modules integrates naturally with Vite because Vite is designed around modern JavaScript modules. Each import and export creates a clear dependency relationship between files.
Compared with the original single <script> version, the modular version does not require putting all the code into one file or relying on global variables and script ordering. Vite can directly follow the module imports, serve the individual modules, transform them as needed, and use that module structure for features such as HMR.

Demo 3

Three transformations Vite applied:

Bundling — multiple JavaScript modules were combined into production assets.
Minification — JavaScript/CSS was compressed by removing unnecessary whitespace and formatting.
Hashed filenames — generated files had names such as index-Bx7K2abc.js instead of the original source filename.

Why use content hashes?
A content hash makes the filename change whenever the file's contents change. This allows browsers and CDNs to cache assets for a long time while still ensuring that a new deployment gets the updated files. For example, if index-abc123.js is cached and a new build produces index-def456.js, the browser knows it is a different file and requests the new version instead of using stale cached JavaScript.

Why not deploy the Vite dev server?
vite dev is designed for development, not production. It performs transformations on demand, provides development features such as HMR, and is not optimized for serving a production application. A production deployment should serve the files generated by vite build using a production web server/CDN. The dev server can also expose development-oriented behavior and source information that should not be part of a production deployment.
